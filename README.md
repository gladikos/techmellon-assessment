# Aegis Airlines — Autonomous Refinement Loop

A self-improving voice AI agent for an imaginary airline (Aegis Airlines) customer service line, built for the TechMellon Forward Deployed Engineer assessment. The system runs a closed loop: simulate a customer call, evaluate the transcript, classify any failures as prompt issues or code issues, automatically rewrite the prompt or patch the backend code, and re-run — until all scenarios pass or the iteration limit is reached.

## What it does (Scenario cycle)

For one scenario at a time, the loop runs up to 5 (configurable constant) iterations of:

1. **Push** the current system prompt to ElevenLabs (always start at baseline prompt)
2. **Simulate** a full call between customer (Claude Haiku) and agent (ElevenLabs - Claude Haiku)
3. **Evaluate** the resulting transcript against four criteria (understanding, tool use, outcome, conversation quality), with each failure classified as either a `prompt` issue or a `code` issue
4. **Fix** what's broken — the prompt fixer rewrites (and/or appends) targeted sections, the code fixer applies find/replace patches to backend files. Both can fire in the same iteration.
5. **Repeat** until all scores reach the configured pass threshold (default 8/10) or `MAX_ITERATIONS` is hit (default 5)

Every run produces a structured JSON log capturing scores, root-cause classifications, what was changed and why, and a delta of performance from first to final iteration.

### Who plays what role

| Role | Played by |
|---|---|
| Airline customer service agent | ElevenLabs Conversational AI (text mode) - Claude Haiku |
| Simulated customer | Claude Haiku |
| Evaluator (scores transcript, classifies failures) | Claude Sonnet |
| Prompt fixer (rewrites system prompt) | Claude Sonnet |
| Code fixer (patches backend files) | Claude Sonnet |

### Project layout


## Quick start

### Prerequisites
- Python 3.10+
- An [Anthropic](https://console.anthropic.com) API key
- An [ElevenLabs](https://elevenlabs.io) API key (free tier is fine for testing)
- [ngrok](https://ngrok.com/download) installed and authenticated

To install and authenticate ngrok:

```bash
# macOS
brew install ngrok

# Windows
choco install ngrok
# or download the binary from https://ngrok.com/download

# Linux
# Download from https://ngrok.com/download or use Snap
```

Then sign up at [ngrok.com](https://ngrok.com) (free), copy your authtoken from the dashboard, and run once:

```bash
ngrok config add-authtoken YOUR_AUTHTOKEN
```
Every free ngrok account gets one **static dev domain**. Find yours at [dashboard.ngrok.com/domains](https://dashboard.ngrok.com/domains) — it persists across sessions, so you only configure the URL in `.env` and ElevenLabs once.

### Setup commands

```bash
# 1. Clone and install
git clone https://github.com/gladikos/techmellon-assessment.git
cd techmellon-assessment
python -m venv .venv # or py -m venv .venv for Windows
python3 -m venv .venv # for macOS users

# Activate the virtual environment:
source .venv/bin/activate          # macOS / Linux
.\.venv\Scripts\Activate.ps1       # Windows PowerShell

pip install -r requirements.txt

# 2. Configure
cp .env.example .env
# Edit .env — set ANTHROPIC_API_KEY and ELEVENLABS_API_KEY at minimum.
# BACKEND_BASE_URL gets filled in after you start ngrok (next step).

# 3. Start the backend
uvicorn backend.main:app --port 8000

# 4. In a second terminal, start ngrok and copy the HTTPS URL it prints into .env as BACKEND_BASE_URL
ngrok http 8000

# 5. One-time ElevenLabs setup (first run only)
#    See "First-time setup" below — you'll need to create an agent and 7 tools.
#    On a fresh account, tools must currently be created manually in the
#    ElevenLabs dashboard. Once they exist, this script attaches them to
#    your agent:
python setup/configure_elevenlabs.py

# 6. Open the observation dashboard in your browser
open http://localhost:8000/        # macOS
xdg-open http://localhost:8000/    # Linux
start http://localhost:8000/       # Windows
```

The dashboard is the primary way to interact with the system. It's observation-only — no manual intervention is possible or needed. Pick a scenario from the dropdown (or click **Run All 10**), then watch the loop run live: every customer turn, every agent reply, every tool call and result, every iteration's scores, the prompt diff between versions, and a complete event log.

The CLI is also available if you want to drive runs without the dashboard:

```bash
python -m refinement.orchestrator --all                                # all 10 scenarios
python -m refinement.orchestrator pet_policy_inquiry                   # single scenario
python -m refinement.orchestrator --list seat_preference cancel_refund # subset
```

## First-time ElevenLabs setup

The pipeline talks to ElevenLabs in two places: it pushes prompt updates to an agent before each iteration, and the agent calls webhook tools (search flights, create bookings, look up policies) against your local backend during simulated calls. You need to set up the agent and its 7 tools once.

### 1. Create the agent

In the [ElevenLabs dashboard](https://elevenlabs.io):

1. Go to **Agents** in the left sidebar
2. Click **Create agent** (or **+ New agent**)
3. Name it something like `Aegis Airlines Customer Service`
4. Set the agent to **Text-only** mode (top right of the agent page) — the refinement loop uses ElevenLabs's text-mode WebSocket; no audio is involved
5. Set the **first message** to: `Thank you for calling Aegis Airlines. How can I help you today?`
6. Leave the **system prompt** blank or as-is — the refinement loop pushes its own prompt before every run, so anything here will be overwritten
7. Copy the **Agent ID** from the URL (it looks like `agent_4601kr0...`) and paste it into your `.env`:
ELEVENLABS_AGENT_ID=agent_4601kr0...

### 2. Create the 7 webhook tools

The 7 tool specs are in `setup/elevenlabs_tools/` as JSON files. Each one points at a backend endpoint via the `BACKEND_URL` placeholder.

ElevenLabs's create-tool API has stricter validation than its dashboard's JSON-export format, so for now tools must be created via the dashboard:

For each `.json` file in `setup/elevenlabs_tools/`:

1. Open the file and replace `{{BACKEND_URL}}` with your actual ngrok HTTPS URL (e.g. `https://abc123.ngrok-free.dev`) wherever it appears in the `url` field
2. In the ElevenLabs dashboard, go to **Tools** → click **Add tool** → choose **Edit as JSON**
3. Paste the entire JSON from the file
4. Save

Repeat for all 7 tools: `get_policy`, `search_flights`, `book_flight`, `get_booking`, `cancel_booking`, `reschedule_booking`, `add_booking_addon`.

### 3. Attach the tools to your agent

Once all 7 tools exist, the setup script attaches them to your agent in one command:

```bash
python setup/configure_elevenlabs.py
```

The script is idempotent — safe to re-run any time. It:
- Lists all tools on your account, matches them by name against the JSONs in `setup/elevenlabs_tools/`
- Attaches the matched tool IDs to the agent identified by `ELEVENLABS_AGENT_ID`
- Falls back gracefully if any expected tools are missing (prints a warning and continues)

After this, your agent is fully configured. The refinement loop is ready to run.

### Note on the URL placeholder

The 7 JSON files in `setup/elevenlabs_tools/` use `{{BACKEND_URL}}` as a placeholder for your backend's HTTPS URL. When you create the tools manually in the ElevenLabs dashboard, replace this placeholder with your actual ngrok dev domain URL (e.g. `https://your-name.ngrok-free.dev`) before pasting each JSON. Since your dev domain is static, you only do this substitution once.

## APIs and tools used

This section lists the stack and explains why each choice was made.

**Backend: FastAPI + raw SQLite**
- `fastapi` + `uvicorn[standard]` for the web server.
- `pydantic` + `email-validator` for request/response schemas.
- **Database: raw `sqlite3`, no ORM.** SQLAlchemy was the obvious alternative but adds dependency weight. Setup with sqlite3 is very simple, and with only 3 tables and 1 joint with a FK it seemed the right choice for this assessment.

**Knowledge base: JSON file, not a vector DB**
The 9 policy topics (pets, baggage, cancellation, etc.) live in `data/knowledge_base.json` and are served by `GET /knowledge/{topic}`. Each topic is keyed by name (e.g. `"pets"`) and returns a structured response with summary, rules, and a description. A simple JSON seemed more convenient than choosing a Vector DB or a RAG. The JSON is structured, therefore there is no semantic-search ambiguity to resolve, it loads very quicly with Python and for this use case it delivered the same correctness guarantees as a RAG without the operational cost or complexity. If the policies grew to thousands of unstrctured data, RAG and VectorDB woud become justified.

**LLMs: Anthropic Claude (mixed models)**
- `claude-haiku-4-5` for the **customer simulator** — chosen for lower latency and cost, since the simulator runs many turns per scenario and doesn't need deep reasoning to roleplay a customer.
- `claude-sonnet-4-6` for the **evaluator, prompt fixer, and code fixer** — chosen because these tasks require careful judgment: faithful root-cause classification, prompt edits, and safe code patches with valid syntax. Sonnet has very good reasoning and seemed the appropriate choice to become the 'correcting' evaluator of our agent.
- I considered using GPT-4 alongside for one of the roles to test multi-model robustness, but adding a second provider adds another API key and billing relationship.

**Agent runtime: ElevenLabs Conversational AI**
- Used per the brief's requirement. The SDK is used for live conversations (its callback model is convenient for streaming agent/user turns to the dashboard); REST endpoints are used directly for control-plane operations the SDK doesn't cleanly expose: pushing prompt updates between iterations (`PATCH /v1/convai/agents/{id}`) and fetching the authoritative post-call transcript (`GET /v1/convai/conversations/{id}`). The authoritative transcript is critical because the SDK's live callbacks only surface agent and user turns, not tool calls and tool results — and the evaluator scores tool use, so it needs that data.

**Tunneling: ngrok**
- ngrok is used to expose the local backend over HTTPS so ElevenLabs can hit the agent's webhook tools. Every free ngrok account gets one static "dev domain" that persists across sessions, which removes the URL-rotation problem that would otherwise require updating tool URLs in the dashboard each time.
- Cloudflare Tunnel was the main alternative — also free, also gives a permanent URL — but ngrok was chosen because it did not seem to have tradeoffs against Cloudflare Tunnel.

**Frontend: vanilla HTML + Tailwind, no framework**
- The dashboard is a single static HTML file with a small amount of Tailwind for styling and Chart.js for visualizations. I chose this over Streamlit (which I had originally scaffolded) because the dashboard's needs are simple: render a few panels, stream WebSocket events, show a diff. Streamlit's tight server-coupling and slow re-renders fight against a real-time event stream. A static HTML page connecting to a WebSocket is faster to implement, faster at runtime, and trivially shippable.
- React/Vue would have been overkill for ~200 lines of UI logic.

**Other utilities**
- `python-dotenv` for env loading.
- `tenacity` for retry-with-backoff on ElevenLabs prompt updates (a failed push between iterations would silently invalidate the next run).

## Tradeoffs made

### Deliberately weak baseline prompt

The baseline `v0.0-bare` is intentionally minimal: no airline name, no behavioral rules, no tool descriptions. Just *"You are a helpful customer service agent for an airline."*

The brief asks for a "basic system prompt." I read this two ways: (a) a competent starting prompt that handles most cases, or (b) a deliberately under-specified one. I chose (b) because the assessment's largest weight (30%) is on whether the loop works — and a strong baseline would mask whether refinement is actually doing useful work. The loop's job is to surface and fix gaps; a competent baseline removes the gaps before the loop sees them. Even though the starting system prompt was meaningfully weak, I came accross countless scenarios where almost all of the scenarios were completed with just 1 iteration, showcasing the capabilities of Claude Haiku (not even the strongest model for reasoning) to exceed expectations.

### Knowledge base as JSON, not a vector DB

Already covered in "APIs and tools used" — the agent always asks for a named, known topic, so a JSON keyed by topic name gives the same correctness as RAG without the operational cost.

### Authoritative transcript via REST, not just SDK callbacks

The ElevenLabs SDK's callback model surfaces agent and user turns in real time but **doesn't expose tool calls or tool results**. Since one of the four evaluation criteria is whether the agent called the right tool with the right parameters, the evaluator needs tool events in its transcript. So the system uses two transcript sources: SDK callbacks for the live UI stream (low-latency dashboard updates), and the REST `GET /v1/convai/conversations/{id}` endpoint for the authoritative post-call transcript that includes every tool event. The evaluator gets the authoritative version; the dashboard back-fills tool events into the live feed once the call ends.

### Duplicate-booking guard at the application layer, not as a UNIQUE constraint

The check `passenger_email + flight_id` for `confirmed` bookings happens inside `create_booking` rather than as a database constraint. A UNIQUE constraint would block re-booking after a cancellation, which would break the cancel-then-rebook flow. The application-layer check correctly excludes cancelled bookings from the duplicate test.

### Passenger rotation across iterations for booking-creating scenarios

For the three scenarios that create new bookings (`book_next_to_destination`, `cheapest_within_week`, `seat_preference`), the simulator persona uses a `{{NAME}}/{{EMAIL}}` placeholder, and the orchestrator rotates through a 5-passenger pool by iteration index. Without rotation, iteration 2 of a booking scenario would always hit the duplicate-booking guard from iteration 1's booking. Rotation lets the loop iterate cleanly without polluting test fixtures.

### Code fixer: exact-match-once with file whitelist and pre-patch backups

The code fixer takes find/replace patches from Sonnet, but only applies them if:
1. The target file is in a whitelist of editable backend files
2. The `find` string matches **exactly once** in the file (zero or multiple matches aborts the patch)
3. A timestamped backup of the original file is written before applying

These constraints were chosen over alternatives like AST-based edits or full file rewrites because they're conservative and recoverable. AST edits would handle structural changes more elegantly but require parsing for every supported language and create more failure modes. Full-file rewrites would let Sonnet redesign whole modules but introduce massive risk of regressions on unrelated code. Exact-match-once is the simplest mechanism that's hard to get wrong, and the safety net of pre-patch backups means a bad patch is always recoverable.

### Two-source orchestrator events: live SDK + post-call REST

Same as the transcript decision but worth calling out at the orchestrator level: agent and customer turns are emitted to the dashboard via WebSocket as they happen (immediate UX feedback), then tool events are emitted in a second wave after `fetch_authoritative_transcript` returns. The user sees a complete picture by the time the iteration's evaluation runs, even though tool events aren't strictly real-time during the call.

### Wipe-and-reseed DB on startup

Every uvicorn restart wipes the SQLite DB and reseeds 350 flights + 4 demo bookings. This is the right tradeoff for an assessment where reviewers run the pipeline live: they get a deterministic fixture state on every fresh start. The downside is that mid-run reloads (triggered by the code fixer patching backend files) can wipe in-flight bookings — but this only affects the rare scenarios that modify a booking *and* trigger a code fix in the same run, and the reseed restores the demo bookings (`AGX-DEMO1..4`) immediately. For a real deployment, the seeder would only run if the DB is empty.

### Orchestrator runs in-process with the backend

The dashboard's WebSocket handler currently spawns the orchestrator as a daemon thread inside the FastAPI process. This works for prompt-only iterations, but when the code fixer patches a backend file, uvicorn's `--reload` watcher restarts the process and kills the orchestrator thread mid-iteration. The CLI invocation (`python -m refinement.orchestrator`) doesn't have this issue because it runs in a separate process. I documented this as a known limitation rather than fixing it under deadline pressure — see "What I'd improve next" for the planned refactor.

### Setup script: idempotent attach, partial-best-effort create

The ElevenLabs setup script `setup/configure_elevenlabs.py` works fully for the list/match/attach paths (verified end-to-end with a tool re-attach test), but the create-tool path hit unfortunate API quirks: ElevenLabs's create endpoint has stricter validation than the dashboard's JSON view returns, with required fields and structural differences I didn't fully reverse-engineer in time. The script handles this gracefully — it warns and continues if a tool can't be created, and the README create the 7 tool webhooks covers the workaround around this issue.

## What I'd improve next

These are honest gaps and improvements ranked roughly by impact.

### 1. Orchestrator as a separate process, not a daemon thread

Currently the dashboard's WebSocket handler spawns `run_pipeline` as a daemon thread inside the FastAPI process. When the code fixer patches a backend file, uvicorn's `--reload` watcher restarts the process and kills the orchestrator thread mid-iteration. The CLI invocation doesn't have this problem because it runs out-of-process. A possible fix for this is to make the WebSocket handler spawn the orchestrator as  a subprocess, although this would require debugging and several code changes.

### 2. Programmatic API ElevenLabs tool provisioning

The setup script's create-tool path hit API quirks — the create endpoint expects a different schema than the dashboard's JSON-view returns: nested object structures rather than arrays, required-but-undocumented fields like `properties.type`, and validation rules like "query_params_schema.properties must have at least one item" that can't be satisfied for tools with no query params. I did some debugging regarding this matter but several issues kept coming back so I chose to configure part of the webhooks form the dashboard. A possible fix for this would be to investgate the payloads and API requests through the DevTools of the dashboard and copy the exact pattern. 

### 3. Stricter evaluator with anchored failure taxonomy

The evaluator occasionally classifies the same underlying behavior under different criteria across iterations of the same scenario. For example, in one of the example runs (`special_assistance`), the same "agent confidently states the 48-hour rule is met when departure is <24h away" failure was filed under `conversation_quality` in iteration 1, `tool_use` in iteration 2, and `outcome` in iteration 4. Each individual classification is defensible but inconsistent across iterations.

The fix is to give the evaluator a small fixed taxonomy of failure types (e.g. `factual_error`, `repetition`, `missing_tool_call`, `policy_violation`, `format_issue`) and require it to anchor its `criterion` choice to that taxonomy. This would also make trend analysis across runs more meaningful.

### 4. Recurring-failure check before declaring convergence

The loop converges when scores cross threshold — but if a specific failure quote keeps appearing across iterations (the agent keeps making the same mistake despite the prompt fix targeting it), the loop doesn't currently treat that as a blocker. A recurring-failure check (same failure surfaces in 2+ iterations → don't converge even if scores pass) would catch the case where the prompt fixer writes correct rules that the agent ignores due to model capability limitations.

### 5. AST-based code patches for safer edits

The current code fixer uses exact-string find/replace, which works when patches are simple and the surrounding context is unique, but fails when the LLM proposes a `find` string that doesn't match exactly once. AST-based patches (e.g. via `libcst` for Python) would let the fixer target functions, classes, or specific statements by structural identity rather than character matching. More complex to implement, but more robust on larger files where exact-match is brittle.
